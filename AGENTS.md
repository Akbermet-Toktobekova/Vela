# AGENTS.md — Vela (FinAgent): единый протокол для всех агентов

Этот файл — канонические правила проекта. Его обязан соблюдать **любой** агент (Claude Opus, Astra GPT 6, Gemini 4 Argon, Gemini Flash 3.8 и любой будущий).
Мастер-спецификация: `FinAgent_Production_Development_Prompt.md`; утверждённые изменения 2026-10-29: `docs/product/PILOT_SPEC.md` (при расхождении продуктового поведения читать новую редакцию). При конфликте: безопасность > этот файл > спецификация > скиллы.

---

## 1. Команда и роли

| Роль | Модель (основная) | Резерв | Что делает |
|---|---|---|---|
| **Orchestrator** (мозг) | Astra GPT 6 / Gemini 4 Argon | Claude Opus 5.5 | Ведёт бэклог, ревьюит, принимает/отклоняет, обновляет статусы, решает «что дальше» |
| **Heavy executor** | Astra GPT 6 | Gemini 4 Argon / Claude Opus | Сложная многофайловая интеграция, безопасность/изоляция (JWT/RLS), асинхронный воркер |
| **Light executor** | Gemini Flash 3.8 | Astra GPT 6 / Gemini 4 Argon | Автономные модули (1–2 файла), чистые функции, схемы/JSON, тесты, конфиги, документация |

- Текущий оркестратор указан в `docs/agents/HANDOFF.md` (поле `Orchestrator`).
- **Наследование:** если у текущего оркестратора закончились кредиты, **Astra GPT 6** (или Argon) становится оркестратором. Он читает скилл `vela-orchestrator` и продолжает с `docs/agents/HANDOFF.md`. Ничего не нужно восстанавливать из памяти чатов: всё состояние лежит в файлах.
- Flash **никогда** не выступает оркестратором и не принимает чужие задачи.
- Если оркестратор (Astra GPT 6 или Argon) сам выполнил задачу, её ревью проводится **в новом чате** (чистый контекст).

## 2. Источники правды (читать в этом порядке)

1. `docs/agents/HANDOFF.md` — где мы сейчас, текущая задача, кто оркестратор, открытые вопросы.
   Затем `PRODUCT_PLAN.md` — общая картина продукта, соответствие видению, карта возможностей и сквозные сценарии. Исходный текст пользователя сохранён в `docs/product/USER_VISION.md`.
2. `docs/agents/BACKLOG.md` — упорядоченный список задач с ID, моделью, областью, критериями приёмки и командами проверки.
3. `docs/agents/reports/<ID>.md` — отчёты исполнителей.
4. `PROGRESS.md` — сводка готового/оставшегося (обновляет только оркестратор).
5. `docs/release-readiness.md` — статус релизных гейтов (обновляет только оркестратор).

Состояние **никогда** не хранится только в чате. Всё, что важно, записывается в файлы выше.

### Поддержание продуктового плана

- После независимого ревью оркестратор обновляет затронутые пункты `PRODUCT_PLAN.md` вместе с BACKLOG/HANDOFF и ссылкой на доказательство. Статусы T-задач канонически хранятся только в BACKLOG; обзор плана не заменяет их.
- Готовый модуль не равен принятому пользовательскому сценарию. Сквозные J01–J12 закрываются по реальному прогону с датой и средой.
- Следовать зависимостям задач, включая T50 перед T31 и T50–T63 перед финальным T46. При крупном срезе сначала создать дочерние карточки с узкими Scope/Acceptance/Verify.
- Предложения P1–P5 в плане не являются автоматически утверждёнными дополнительными функциями. Финансовые значения, платные сервисы и допуск к публикации остаются решениями пользователя.

## 3. Команды пользователя (пользователь сам переключает модели)

| Фраза пользователя | Кто | Что делать |
|---|---|---|
| `Выполни T<NN>` | Flash / Astra GPT 6 / Argon | Скилл `vela-executor`: выполнить задачу, записать отчёт, поставить статус `review` |
| `Проверь T<NN>` | Оркестратор | Скилл `vela-orchestrator`: ревью → `done` или `rework` |
| `Что дальше?` | Оркестратор | Прочитать HANDOFF + BACKLOG, назвать следующую задачу и нужную модель |
| `Прими роль оркестратора` | Astra GPT 6 / Argon | Взять роль, обновить поле `Orchestrator` в HANDOFF, продолжить |
| `Чекпоинт фазы <N>` | Оркестратор | Полный прогон проверок, обновление PROGRESS и release-readiness |

## 4. Статусы задач в BACKLOG

`todo` → `in_progress` → `review` → `done`
Ответвления: `rework` (вернули с замечаниями), `blocked` (нужен пользователь/доступ), `escalated` (Flash не справился → Astra GPT 6 / Argon).

Менять `review` → `done` может **только оркестратор**.

## 5. Жёсткие правила для всех исполнителей

1. **Одна задача за сессию.** Трогать только файлы из поля `Scope` задачи. Если нужно выйти за scope, остановиться и записать это в отчёт как вопрос.
2. **Не угадывать.** Неясное требование → статус `blocked` + вопрос в отчёте. Не придумывать финансовые правила, веса и пороги.
3. **Деньги — только целые минимальные единицы с явной валютой** (`int`, EUR/HUF в новом контракте; legacy EUR сохраняет совместимость). Курсы — Decimal; выписки никогда автоматически не меняют балансы. Никаких `float` в финансовой логике. Не ломать инварианты из `services/api/vela/domain.py`.
4. **Не удалять** существующий код, тесты, комментарии и документацию без явного указания в задаче.
5. **Никогда:** не публиковать, не деплоить, не трогать продакшн-данные, не коммитить секреты (`.env`, `.local/`), не покупать сервисы, не ставить глобальные пакеты без задачи.
6. **Не фабриковать результаты.** В отчёт идёт только реальный вывод реально запущенных команд.
7. **Новые зависимости** только если они явно указаны в задаче. Иначе статус `blocked` + вопрос.
8. После изменения API обязательно: `python scripts/generate-contracts.py` и проверка drift.
9. Перед началом и после окончания задачи: `git add -A; git commit -m "<ID>: ..."` (после T00). Один коммит на задачу, чтобы откат был простым.
10. Flash: если задача не получилась за 2 попытки, или оказалась сложнее описанного, ставит `escalated` и останавливается.

## 6. Обязательные проверки (Definition of Done)

Минимум для любой задачи с кодом:

```powershell
python scripts/check.py                      # все backend-тесты зелёные
cd apps/mobile; npm run typecheck; cd ../..  # 0 ошибок TS (если трогали mobile)
python scripts/generate-contracts.py         # если трогали API; 0 drift
```

Плюс команды из поля `Verify` конкретной задачи. Число тестов не должно уменьшаться.

## 7. Формат отчёта исполнителя

Файл: `docs/agents/reports/<ID>.md` (шаблон: `docs/agents/reports/_TEMPLATE.md`). Обязательные поля:
статус, модель, что сделано, изменённые файлы, команды проверки с реальным выводом, отклонения от задачи, риски, вопросы оркестратору.

## 8. Карта проекта

- `services/api/vela/` — FastAPI + финансовое ядро (`domain.py`, `store.py`, `main.py`, `imports.py`, `chat.py`, `ai.py`)
- `services/api/tests/` — pytest-тесты
- `apps/mobile/` — Expo SDK 58, Expo Router, `src/app/` (экраны), `src/lib/api.ts`, `src/lib/generated.ts` (генерируется)
- `contracts/openapi.json` — генерируется, руками не править
- `scripts/` — `check.py`, `generate-contracts.py`, `smoke-gemini.py`, `run-api.py`
- `policies/` — версионные политики/каталог действий
- `docs/agents/` — протокол команды, бэклог, хэндофф, отчёты

## 9. Скиллы проекта

- `.agents/skills/vela-orchestrator/` — для оркестратора (ревью, выбор следующей задачи, наследование роли)
- `.agents/skills/vela-executor/` — для Argon/Flash (выполнение одной задачи)
- Вспомогательные: `surgical-patch` (мелкие фиксы), `lean-build` (новые фичи), `migration` (схемы/БД), `safe-refactor`, `investigate-first` (непонятные баги), `verify-and-stop` (только проверка).
