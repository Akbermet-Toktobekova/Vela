## Что сделано
- Создан тестовый модуль `services/api/tests/test_acceptance_fixture.py`, фиксирующий эталонный приёмочный сценарий из спецификации (§9, строки 357–368).
- Все числовые значения заданы строгими целочисленными литералами в центах EUR без вызова производственного калькулятора:
  - Баланс 400 + доход 600 = 1000 EUR (`CONFIRMED_INITIAL_BALANCE = 40_000`, `NEW_INCOME_AMOUNT = 60_000`, `EXPECTED_POST_INCOME_BALANCE = 100_000`). Повторное добавление выписки/транзакции не удваивает баланс.
  - Обязательства на горизонте: аренда 600 EUR (`60_000`), необходимые расходы на жизнь 150 EUR (`15_000`), обязательный платёж по долгу 50 EUR (`5_000`), защищённый остаток 100 EUR (`10_000`).
  - Доступная ёмкость (discretionary allocation): ровно 100 EUR (`10_000`).
  - Аллокация 150 EUR (`15_000`) не проходит проверку доступности (`ValueError` / preview `eligible: False`).
  - Аллокация 40 EUR (`4_000`) проходит, оставляя ровно 60 EUR (`6_000`) свободной ёмкости.
  - Принятие шага фиксирует `planned` резервирование на 40 EUR, баланс счёта не меняется.
  - Подтверждение завершения заменяет `planned` на `saved` 40 EUR без двойного списания; ёмкость остаётся 60 EUR; внутренний перевод не меняет общий объём активов.
  - В отдельной ветке до принятия: добавление нового обязательного расхода 80 EUR (`8_000`) снижает ёмкость до 20 EUR (`2_000`), делая рекомендацию на 40 EUR невалидной.
  - Медленная фоновая задача (slow job) с устаревшей ревизией отклоняется с кодом 409 Conflict.
- Реализованы 2 класса тестов: `TestSection9DomainAcceptanceFixture` (чистая доменная логика) и `TestSection9WorkflowAndConcurrencyAcceptanceFixture` (HTTP API и защита от гонок).
- Производственный код не модифицировался (строго в рамках задачи T10).
