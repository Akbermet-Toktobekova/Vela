## One mode and explicit trusted configuration

Use **`APP_MODE` only**. Preserve current unset/`demo` behaviour for existing isolated legacy compatibility, treating `demo` as a deprecated local-only alias; `local` is the preferred synthetic mode. Add an explicit `cloud` mode and reject unknown modes. Ignore no parallel `APP_ENV` bypass. In cloud mode never accept DEMO_API_TOKEN or return `local-demo`, even if that environment value is present. Existing local tokens do not migrate to JWT sessions.

Cloud configuration consists of API database URL, Supabase Auth base/project URL, expected JWT issuer, audience, trusted JWKS URL and explicit allowed signing algorithm(s). Keep public project/publishable key separate from secret database/backend credentials; no service-role key in mobile, token URL, logs or exports. Issuer/audience/JWKS values must come from the approved project's actual Auth configuration and agree with that project. A JWT header's `alg`, `jku` or `x5u` cannot override them; `none` and unexpected algorithms fail. Do not accept arbitrary issuer/key endpoints from a client or token.

For asymmetric Supabase signing keys, use the project's configured public JWKS and `kid` selection, validating the actual configured algorithm. Cache trusted public keys with bounded network timeouts, handle key rotation through a refresh on unknown `kid`, and reject unresolved/malformed keys. Do not guess an algorithm or silently accept legacy shared-secret tokens. If the selected project still requires a legacy symmetric key, record that as an explicit configuration/security-review decision before implementation rather than introducing an automatic HS/RS fallback. Tests use generated asymmetric keys and an injected JWKS response; no real project/key is required to implement the verifier.

## OTP, refresh and logout boundary

Use **Supabase Auth email OTP**, not custom API-issued OTPs/passwords. The adapter must expose request-code(email), verify-code(email,code), refresh-session and sign-out, with provider errors mapped to calm invalid/expired/rate-limited/unavailable states. Send/verify/refresh/logout use the configured Supabase Auth service with its public client key; only the resulting access JWT goes to Vela API. Exact provider request/response schemas and cooldown/error metadata must be checked against official Supabase documentation when implementing; this preflight is deliberately restricted to repository sources and does not invent those wire formats or numeric cooldowns.

T32 supplies a testable adapter/backend contract; T52 owns visible resend/change-email/expired-code/session-resume/sign-out/account-cache flows. Logout must clear local access/refresh data even if the remote operation fails, reporting that remote outcome honestly. Document that locally verified access JWT validity/revocation semantics depend on provider configuration; do not promise immediate server-wide revocation without implemented evidence. No emails, accounts or cloud sessions are created for these tests.
