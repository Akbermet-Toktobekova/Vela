# Vela current data map

2026-10-29, T44; migration0003/current store and T51 JSON profile. Exactly **eight private SQL tables** exist in the application store. `alembic_version` is schema bookkeeping, not a ninth user aggregate. Separate local quota tables and external provider/device stores are listed below. This is a source inventory, not a scan/export of real databases.

## Private application SQL records

1. **demo_state** — key owner; integer revision plus opaque State JSON. Includes legacy snapshot/actions/deferred/history/income identities/debts/analytical transactions and personal aggregate. Personal includes explicit EUR/HUF accounts/balance dates/received-income effects, canonical EUR planning goal/bills/reservations/completed steps, optional T51 profile details/provenance/confirmation dates/expected-income estimate or range/preferences/restrictions/onboarding/version counters. Unknown remains null/unknown, not inferred financial zero. Expected income is not received cash. Direct and legacy adopted financial records remain distinct; old snapshot is retained for export/history, not current writable cash after adoption.
2. **command_receipt** — composite owner/key; command fingerprint and serialized response. Can contain financial/profile/lesson response data; private and retained until owner data deletion. Exact replay is scoped to owner and body fingerprint; not an anonymous audit table.
3. **import_preview** — owner/id; parsed preview JSON with filename, dates/currency, transactions/descriptions/references, analytical totals/warnings/recurring candidates/parser/model. Preview can contain PII even when AI text was masked. Synchronous upload keeps a limited preview set; durable worker publication has its own lifetime. No claim that previews expire with original bytes or remain forever independently of cleanup/deletion policy.
4. **coordination_run** — owner/run ID; input financial revision, status and serialized specialist/coordination result. Treat reasons/calculation context as private derived data, not confirmed financial events or hidden model chain-of-thought. No proof all new Today/Assistant journeys consume a final shared publication yet.
5. **published_recommendation** — owner/publication key; financial revision and serialized published card/result. Immutable-style publication identity/transaction guards exist, but end-to-end newer specialist/goal execution integration remains its own tasks. It is not a second balance source.
6. **private_original** — owner/file UUID; backend-target fingerprint, opaque object key, SHA256, size, creation/expiry seconds and pending/ready/delete_pending state. Contains no original filename/token. It preserves denied cleanup intent after financial-state erase until physical deletion confirms. Target fingerprint binds actual root or origin+bucket, not secret credential.
7. **import_generation** — owner/current random generation, created on first job enqueue. Delete removes it transactionally; later explicit enqueue creates a new generation so old workers cannot publish into the new owner dataset. It is not an authentication account, permanent identity tombstone or account-deletion retention guarantee.
8. **import_job** — owner/job UUID plus unique owner/enqueue key, fingerprint, generation, original UUID, version/status/attempt/retry/lease/timestamps and private JSON payload. Payload carries original filename/content type, checksum, parser version, external-AI choice/notice version, stage/safe error, result-preview identity and job-command receipts. No source bytes/access/refresh/service token or raw provider error is stored in the row. Lease tokens and private filenames never appear in public job status.

All private store keys/predicates derive from verified owner. Local mode deliberately uses one `local-demo` identity; that mode is not multi-user isolation. Cloud owner comes from validated JWT subject and never auto-maps existing local rows. Database credentials/privileged operators can access the whole store; backend tests do not establish deployed RLS/encryption/backup security.

## Other persisted and transient locations

- **Original bytes:** isolated local filesystem outside webroot, or configured Supabase private Storage. Paths use hashed owner and fresh file UUID, never raw filename. Retention requires explicit permission. Exactly30-day expiry denies API reads independently of physical deletion; confirmed analytical rows survive original-only deletion. No public/signed URLs. Provider backup/residual-copy policy remains T70/T62 evidence.
- **Quota SQLite:** app/worker-selected quota.db contains `usage(model,ts,day,tokens)` and `cooldown(model,until)` plus an index. It is ownerless application-level operational accounting, with no raw statement/messages/amounts. Time/model activity may still be sensitive; ownerless is not proof of anonymity. DELETE/v1/data does not erase these shared counters. Separate directories/hosts/provider clients are not automatically one shared quota.
- **Device credentials:** session adapter keeps access tokens in memory; native refresh credentials use deployment-scoped SecureStore, web refresh/access stays in memory. Existing local connection token follows local connector rules. Actual secure-device persistence/OS backup, sign-out/cache clearing and cross-device UI remain T52/T63. No backend export includes credential secrets.
- **Supabase Auth:** provider stores email/OTP/session/account data outside this application database. Public project/client settings differ from backend service/database keys. Local erase of Vela financial data is not proof of provider Auth account/session/backup deletion or immediate global JWT revocation. Provider lifecycle evidence belongs to T70/T62.
- **Gemini:** may receive consented masked text/context/calculator outputs, or explicitly allowed document processing subject to global raw-document policy. pii.py/generate masking is a reduction mechanism, not a universal anonymizer. Provider request/retention/account policies remain external evidence; no live call is made for this inventory.
- **Chat memory:** current requests/history and fallback/tool context are transient application/model-call inputs. Persistent owner conversation/message tables/history under T59 are planned, not present in these eight SQL tables. Do not claim cross-device permanent Assistant history now.
- **Request logs:** allowlisted event/correlation ID/method/route-template/status/duration; body, raw path/IDs/query, financial text, credentials and traceback are not serialized by the request formatter. Worker CLI emits generic operational failure. Reverse proxy/provider/OS/crash logs need separate deployment review and retention rules.
- **Exports/artifacts/backups:** GET/v1/export currently serializes State JSON only. Export files/downloads and synthetic test artifacts are additional copies controlled by the user/operator; server erase cannot revoke an already downloaded file. Complete all-entity export/originals/jobs/provider backups and tested restore are T62 gaps, not implicitly implemented.

## Input, consent and egress paths

Manual financial/profile input passes authenticated strict API models to owner State; confirmed commands use shared revision/idempotency. Imported historical rows enter previews/analytics and never confirm balance or execute money. Original retention and external-AI processing are separate choices; the jobs request persists its processing notice/version. A client field does not prove the screen showed a suitable notice: T52/T61 review that UX/content.

Durable import first stores job/source intent, then private metadata/bytes, then queues leased parsing. Worker publishes only a preview under final owner-generation/lease/active-source guards. False AI permission blocks every external import branch despite global enable flags. Cloud synchronous import endpoints without a processing-consent contract parse locally only; local legacy behaviour stays explicit. Source bytes never enter job SQL payloads or financial logs.

FX requests send currency pair/date to the ECB-specific public quote service, not account balances/owner/documents. Converted Decimal estimates remain read-only display values. Operational/PII risks for other providers are not erased by this limited FX egress.

## Deletion and retention semantics

`DELETE /v1/data` transactionally deletes that owner's jobs/generation and original five financial/receipt/preview/run/publication tables. Original records are not blindly erased from SQL: own files deny reads and physical deletion is attempted, retaining delete_pending metadata on failure. A202 response means pending cleanup, not all bytes gone; retry/worker maintenance can finish. Owner B's records remain. Local shared quota counters remain; external Auth/provider backups/downloads are outside this endpoint's current guarantee.

Original-only delete leaves confirmed analytics/financial records intact. Expired/pending/deleting originals deny access before provider requests. Worker cleanup protects live upload leases and rechecks current metadata; stale workers cannot publish after owner generation deletion/recreation or source expiry/deletion. Physical provider I/O can finish after an earlier erase response; full crash/in-flight/restore lifecycle still requires T62.

No whole-database working downgrade/delete is a migration strategy. Versioned migrations preserve existing row payloads; destructive cycles use disposable synthetic fixtures only. A rollback/restore must pair compatible schema/application and preserved isolated data, including external objects/jobs and deleted-owner safety. Actual provider backup erasure/time promises are unapproved without evidence.
